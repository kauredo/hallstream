# Contract between the parts of Hallstream

Four parts are built in parallel from this file. If a part needs something not written here, it adds it here in the same change and says so.

- `internal/…` + `cmd/hallstream` (Go): Bluetooth reader, live state, storage, FPB client, HTTP server.
- `web/overlay/` (HTML/CSS/JS, no build step): the one OBS Browser Source.
- `web/painel/` (HTML/CSS/JS, no build step): the control panel.
- FPB Calendar (Ruby, separate repo): two new endpoints.

`web/` is embedded in the binary with `go:embed`. No framework, no npm, no CDN at runtime: the PC at the club may be offline. Fonts live in `web/fonts/` as woff2 (Graduate, Barlow 400/500/600, Barlow Condensed 500/600/700/800, all OFL).

## Server
- Listens on `127.0.0.1:8765`; if taken, the next free port up to 8775. With `settings.phone_access` on, listens on `0.0.0.0` and every `/api/*` write and `/painel` require the PIN (cookie `pin` or header `X-PIN`); `/overlay` and `GET /api/state` stay open on localhost only.
- On start, opens `http://127.0.0.1:<port>/painel` in the default browser. Before listening it asks each port from 8765 to 8775 for `GET /api/hello`; when one answers as another Hallstream it opens that one's panel and exits. See "App on Windows".
- `GET /` → redirect to `/painel`.
- `GET /overlay` → `web/overlay/index.html`. Query `?screen=<name>` forces a screen (for previews and tests); `?state=<url>` loads state from a JSON file instead of SSE (tests).
- `GET /painel` → `web/painel/index.html`.
- `GET /media/<file>` → files in `dados/media/` (logos, crests, player photos).
- `GET /assets/<file>` → `web/assets/` (embedded): `crest.svg`, `crest.png` (a neutral stand-in shield with a star, for any sport, for the home crest), `hallstream-lockup.svg` (the Hallstream lockup in Soalho, for the panel's dark top bar), `icon/` (the app icon, favicons and `hallstream.ico`, made by `brand/icons.sh`), `pavilhao-demo.jpg` (a synthetic basketball court, the tinted backdrop of the full screens, and the camera stand-in for `?preview=foto`), `pavilhao-neutro.svg` (the same floor with only the middle line, the backdrop for other sports).
- `GET /overlay/<file>` → `web/overlay/<file>` (embedded): `overlay.css`, `overlay.js`, `fixtures/…`. `GET /overlay/` (trailing slash) serves `index.html` too. Added by the overlay: the page links `/overlay/overlay.css`, `/overlay/overlay.js` and `/fonts/fonts.css` by absolute path, because relative links from `/overlay` (no slash) would resolve against `/`.
- `GET /fonts/<file>` → `web/fonts/` (embedded): `fonts.css`, the woff2 files, `OFL.txt`. The panel can link `/fonts/fonts.css` as well.
- `GET /painel/<file>` → `web/painel/<file>` (embedded): `painel.css`, `painel.js`, `mock.js`. `GET /painel/` serves `index.html` too. Added by the panel: it links these by absolute path, for the same reason as the overlay.
- PIN, added by the panel: `GET /painel` (the static HTML) is always served, since it holds no data; the PIN guards `/api/*` and `/api/events`. A request without a valid PIN gets `401 { "error": "…" }`. The panel then shows its PIN screen, sets the cookie `pin=<4 digits>; path=/` and retries. It uses the cookie, not `X-PIN`, because `EventSource` cannot send headers.
- `GET /i18n.js` → `window.I18N = {…};`, every key with its string in `settings.lang` (see "Words"). `GET /i18n/<file>` → `web/i18n/` (embedded): `i18n.js`, `pt.json`, `en.json`.
- More overlay query params, for tests only: `?preview=1` (dark background behind the transparent page) or `?preview=foto` (the demo hall photo), `?now=<ISO time>` (fixes the clock for the opener countdown), `?anim=0` (no transitions or animations: every element draws in its final state at once, scores without count-up). A forced `?screen=` shows without its entrance.

## Words (i18n)
Every string a person reads, in the panel, the overlay, the result and thumbnail images, the API errors, the tray and `dados/marcador.log`, lives in `web/i18n/pt.json`, with the English in `web/i18n/en.json`. Code and comments stay in English.
- The file is one flat JSON object of dotted keys to strings, sorted by key: `"overlay.final.titulo": "RESULTADO FINAL"`. A placeholder is `{name}`. A plural is two keys, `….um` and `….outros`, and the code picks one. A key is always written in full where it is used; a list of keys (weekdays, sports) names each one.
- `settings.lang` (default `"pt"`) names the file. `PUT /api/settings` saves it in lower case, and anything that is not a language name (`pt`, `en`, `pt-br`) as `pt`. A language without a file, and any key its file lacks, read `pt.json`. `en.json` (British English) ships too, and any other `web/i18n/<lang>.json` in the build is picked up. Each file names its language in its own words under `data.nome`; `GET /api/status` → `"langs": [{ "code", "name" }]` lists them, Portuguese first, and Definições offers them in a select that saves and reloads the page. A new language takes effect for the log and the API at once, and in the pages at their next load.
- Go: `internal/i18n`. `i18n.T(key, "name", value, …)` fills the placeholders (an error as its message); `i18n.Err(key, …)` is an error that wraps the errors among its values; `i18n.Key(key)` is a sentinel error whose message is read when it is shown. All three are safe from any goroutine.
- Browser: both pages load `/i18n.js` and then `/i18n/i18n.js` with plain `<script src>` before their own scripts, so the words are there before anything draws (the overlay must never show half its words). `i18n.js` gives `t(key, vars)` and, at once, fills the static HTML: `data-i18n="key"` sets the text, `data-i18n-html="key"` the HTML (copy with `<b>`, `<code>` or a link in it), and `data-i18n-attr="placeholder:key;aria-label:key"` the attributes. Those elements are empty in the HTML. `Intl` dates use the locale in `data.locale`.
- `web/painel/mock.js` stands in for the server and keeps its data and error messages as they are, like the fixtures.
- `go test ./internal/i18n` fails on a key used in a `.go`, `.js` or `.html` file but missing from `pt.json`, a key in `pt.json` nothing uses, a key built at run time, a `pt.json` that is not valid sorted JSON, another `web/i18n/*.json` without exactly the keys of `pt.json`, and a Portuguese-looking string left in `web/painel/*.js`, `web/overlay/*.js`, their `index.html` or non-test Go code (a short list in the test names the data that only looks like copy).

Rules the Go side owns (the overlay never computes them):
- `game.home/away.name` are the names to show. With no game picked they are the console names (`live.home_name/away_name`). Max 20 characters for the opponent's `name` (12 for `settings.club.name`); `short` max 4. The corner scoreboard shrinks a name down to 16 px and shows `short` instead when it would go smaller (about 17 characters and up); every other screen shrinks the name to fit.
- `away.crest_url` is `null` when there is no logo: the overlay then shows `initials` in the tile. Never the word "Emblema".
- `away.color` is always a colour with white text at ≥ 4.5:1.
- `periods` holds completed periods only, in order. Period N's score is the score at the moment the period value changes from N to N+1, or when the clock reaches 0 in period ≥ 4 and stays there 60 s with no new period (basketball; other sports follow `game.rules`). `home`/`away` are that score; `home_points`/`away_points` are the points scored in the period: that score minus the one at the end of the last recorded period (0 before the first), never below 0, so a correction that takes the score under the last period's end gives 0.
- A clock that counts up (`game.rules.count_up`, handball) follows the same screens with its own tests: the clock has started when it rises (`live.clock` above the last frame's, not just a first frame in a new period, so the first frame of the second half at 30:00 leaves `intervalo` on and the next, at 30:01, returns to `marcador`); the game's end is the clock at or past `live.period_end` (`game.rules.length` plus the period's start when a frame has none) in the last regulation period or later, held for `final_hold` before `final`; a count-up with `stop_at_end` false never holds. `live.period_end` is that end in tenths, 0 for a countdown.
- `live.suspensions` is the running suspensions, `[{ "team": "home" | "away", "id": 1, "number": "7", "left": "01:23" }]`, home first; `number` is `""` until the scorer adds it; it is `[]` or `null` before the first one and for every sport without suspensions, and the overlay reads a missing or `null` list as empty. It comes from the phone scorer only (a console sends none). The timeline gets a `suspension` event (`team`, `number`) for each ID above the highest one it has told, a mark that only goes up (so ending a suspension early and undoing that tells nothing twice) until a new game, which numbers them from 1 again. The demo tells nothing. At start, with the phone as the input, the state is primed with the restored scorer's frame (`Machine.Prime`), so the suspensions it still holds are on air at once and are not told as new.
- `live.over`, `live.stoppage`, `live.cards` and `live.subs` are soccer's (`game.rules.cards`); they are `false`, `0`, `[]` or `null` for every other sport, and the overlay reads a missing or `null` list as empty. They come from the phone scorer only. `over` is the scorer's "Fim do jogo". `stoppage` is the minutes of added time announced for this half (0 to 15). `cards` is `[{ "id": 1, "team": "home" | "away", "number": "9", "kind": "yellow" | "second_yellow" | "red", "minute": "45+2'" }]` and `subs` is `[{ "id": 2, "team": "home", "out": "7", "in": "14", "minute": "60'" }]`, both in the order they happened. Every entry carries an `id` that the scorer never gives out twice in a run (undo does not take it back). The minute is written when the card is entered, "23'" up to the half's end and "45+1'" past it, so changing the period length later leaves it as it was. A frame whose list is not JSON reads as none; entries beyond the hundredth, or for a team that is neither `home` nor `away`, are dropped.
- Soccer has no hold at the end (`final_hold` 0, a count-up with `stop_at_end` false): the game is over when `live.over` is true in the last regulation period. That shows `final` and records that period once (and `over` back to false takes it back: the screen goes back to `marcador`, the period is dropped from `periods` and from `dados/periods.json`, so ending the game again records it once). A clock that sits at 90:00 or later, stopped, never ends the game by itself. Picking another game (a new game) sends the scorer `new_game` when the game is soccer or when the scorer still holds a soccer game's cards, substitutions, added time or end, and takes a program-picked `final` screen back to `marcador`; the told marks of cards and substitutions start from 1 again once the last game's entries are gone from the live state. The timeline gets a `card` event (`team`, `number`, `kind`, `minute`) and a `sub` event (`team`, `out`, `in`, `minute`) for each ID above the highest it has told for that list, a mark that only goes up; the demo tells nothing, and the primed state at start (`Machine.Prime`) keeps a restored game's cards and substitutions from being told as new.
- `sets` holds the finished sets of a sets sport (volleyball), in order: `{ "set": 1, "home": 25, "away": 20, "winner": "home" }`. It is `[]` for every other sport and before the first set ends.
  - A set whose score is unknown (seeded from a console, which sends only the counts) has `home` and `away` 0 and its `winner` set.
  - `live.home_sets` and `live.away_sets` are the sets each side has won (clamped to 0 to `2 * sets_to_win - 1`), `live.serve` is `"home"`, `"away"` or `""`, and `live.sets` is the phone scorer's finished sets as it sent them (`"25-20h,18-25a"`). In a sets sport `live.home`/`live.away` are the points of the current set, `live.period` is the current set's number and `live.clock` is `""`.
  - The state machine records a set when `home_sets + away_sets` rises: from `live.sets` when the phone scorer sent it, else (the console) with the points that were on the board just before the count rose. The winner is the letter after the points (`h`/`a`); with none, the side with more points; with a tie (a 0-0 set) the counts say who won.
  - When the count falls (an undo) the sets beyond it are dropped. A frame with neither `home_sets` nor `away_sets` (a console that has not sent them) changes nothing.
  - A sets sport has no automatic `intervalo` between sets (the volunteer can show it by hand).
  - When a side reaches `game.rules.sets_to_win` sets the screen switches to `final` at once, with no hold, and only once. When the count falls below that again (an undo across the match end) the screen goes back to `marcador`, and finishing the match again fires `final` a second time.
- `screen.current` is one of `marcador`, `abertura`, `plantel`, `desconto`, `intervalo`, `final`, `apoiantes`, `proximo`, `voltamos`, `promo`, `nada` (nothing shown). `promo` is only set by `POST /api/promo/:id/show`, never by `POST /api/screen` (see "Promo videos"). `proximo` and `voltamos` are only ever picked by hand (see "Próximo jogo and Voltamos já"). `apoiantes` ("Nossos apoiantes · Juntos pelo clube") shows every sponsor of the game, large; it is only ever picked by hand. With `auto` on (basketball; other sports follow `game.rules`): period 2 ends → `intervalo`; the final condition above → `final`; a period ≥ 3 starts after `intervalo` → `marcador`. Manual changes always win until the next automatic trigger. (Go: a period "starts" when its clock first counts down. An overtime that starts after `final` also goes back to `marcador`, since FIBA gives 2 minutes before overtime and `final` fires at 60 s.)
- `lower_third.visible` turns false by itself at `until`.
- `camera` is where the camera picture sits, in overlay px, at full screen (`full`) and on `desconto` (`window`), when the program moves the camera in OBS (see "Time-out squeeze"). `null` when it does not (OBS off, two-scene mode, camera not found yet).
- `input` is `settings.input`, where the score comes from: `console` (the box) or `manual` (a phone). See "Score input". `box.connected` is the input's: the box linked for `console`, the scorer's phone heard from in the last 60 s for `manual`. `box.scan` is always the Bluetooth reader's. `live.home_timeouts`/`away_timeouts` are the timeouts taken; only `manual` counts them, the box sends 0, so the overlay shows timeout marks only when `input` is `manual`.
- With `box.connected` false the last live values stay and the overlay shows a small grey dot on the scoreboard. The same dot shows when the program itself stops answering (closed, crashed): 7 s after `/api/events` fails with no state since, until a state arrives again by the stream or by the 2 s poll of `/api/state`.
- Team fouls use 4 pips: pips filled = min(fouls,4), all gold at 4+, the number shows the real count.
- `game.theme` is the overlay's colours, made from `settings.club.primary` and `.secondary` by `club.Theme` (`internal/club`), keyed by CSS custom property name without the `--`. The overlay sets each one on `:root` whenever the state brings a different theme, so a club that changes its colours shows them on air without a reload; a key the theme lacks falls back to the value in `overlay.css`, whose `:root` holds the default club's theme (a test keeps the two equal). `red` is the primary as typed; `kit` (score cells), `blood` (label strips, hard shadows), `ink` (near-black backdrop), `tint` and `tint-dim` (the multiply over the hall photo) are darker shades of it; `red-hi` is the primary lightened to 5.5:1 on `ink` (text on dark grounds), `red-lo` lightened to 5.5:1 on `navy` (small labels), `red-text` darkened to 4.5:1 on white (text on white plates). `navy` is the secondary darkened until white text on it reaches 12:1. `on-red` and `on-kit` are the text on `red` and `kit`: white when it reaches 4.5:1, else whichever of white and `ink` reads better. `red-rgb`, `hi-rgb` and `ink-rgb` are `"r,g,b"` for `rgba()`. `lift` and `lift-2` are the primary one and two steps lighter, brought back towards it until their text (`on-lift`, `on-lift-2`) reads at 4.5:1; a dark club has no room for deeper shades, so a style that layers tones of the club colour steps up through these instead. `tone` is `dark` (the primary's HSL lightness under 25%), `light` (dark text on the primary) or `mid`; it is no colour, so the overlay puts it on `<html data-club-tone>` (`mid` without a theme) and sets no custom property for it. The names come from the first look, where the club colour was red and the second navy. The panel's thumbnail and result images (`miniatura.js`, `resultado.js`) draw with the same `game.theme`.
- `game.sport`, `game.sport_label` and `game.rules` come from the game's escalão (`group.sport`), else the club's main sport (`settings.club.sport`). `game.sport_label` is the word the overlay shows next to the club's name (`BASKET`). The labels, by sport: basketball BASQUETEBOL, shown `BASKET`; futsal FUTSAL; handball ANDEBOL; volleyball VOLEIBOL; soccer FUTEBOL. Basketball, futsal, handball and volleyball can be picked today. The overlay puts `game.sport` on `<html data-sport>` (`basketball` when empty). The court marks are basketball's alone: for any other sport the stand-in hall is `pavilhao-neutro.svg` (a floor with only the middle line) and Pavilhão draws no circles, keys or arcs, ending the floor with a straight painted line. A club's own hall photo replaces either stand-in.
- `game.rules` is the sport's profile (`internal/sport`), the same numbers the Go side reads, so the pages never hard-code a sport. Times are in tenths of a second. `id` is the sport; `periods` the regulation periods; `half` the period after which the half-time break falls; `length` the tenths in a regulation period; `clock_down` whether the clock counts down; `fouls_reset` whether team fouls go back to 0 each period; `foul_warn` the fouls at which the pips turn hot (0 = never); `foul_bonus` the fouls from which the other side shoots (0 = never); `shot_clock` whether the sport has a shot clock; `final_hold` the tenths the clock sits at 0 in the last period before the game is over; `timeouts` the timeouts per team in the first half, the second half and each overtime; `overtime_length` the tenths in an overtime period (0 = the regulation `length`); `fouls_carry` whether the fouls of the last regulation period run on through overtime; `period_word` which period labels the pages use, `"quarter"`, `"half"` or `"set"`; `foul_marks` the foul marks the scorer's page draws per team (0 = no fouls row); `max_point` the most one score action adds (basketball 3; futsal and volleyball 1; the scorer's page shows only +1 when it is 1); `foul_penalty` the word on air at `foul_bonus`, `"bonus"` (BÓNUS) or `"free_kick"` (LIVRE; DFK in English, the direct free kick from the 6th foul). `scoring` is `"points"` (basketball) or `"sets"` (volleyball); for `"sets"`, `set_points` is the points that win a set (25), `last_set_points` the points that win the deciding set, the one numbered `2 * sets_to_win - 1` (15), `sets_to_win` the sets that win the match (3, best of 5) and `win_by` the lead a set needs (2). Every other sport has `extra_time` true (volleyball has no periods to run past) and `stoppage_max` 0, and `period_next` past the last regulation period is refused where `extra_time` is false. Basketball's values are `4, 2, 6000, true, true, 4, 5, true, 600, [2, 3, 1]` with `scoring` `"points"`, `max_point` 3, `overtime_length` 3000 (FIBA: 5:00), `fouls_carry` false, `period_word` `"quarter"`, `foul_marks` 5 and `foul_penalty` `"bonus"`. Futsal's (FIFA) are `periods` 2, `half` 1, `length` 12000, `clock_down` true, `fouls_reset` true, `fouls_carry` true, `foul_warn` 5, `foul_bonus` 6, no shot clock, `final_hold` 600, `timeouts` `[1, 1, 0]`, `max_point` 1, `overtime_length` 3000, `period_word` `"half"`, `foul_marks` 5, `foul_penalty` `"free_kick"`: two halves of 20:00 on a stopped clock, one timeout per team per half and none in extra time, accumulated fouls per half (the 5th is the warning, the 6th gives the other side a free kick without a wall) that carry from the second half into extra time, and extra time in periods of 5:00. Soccer's (IFAB) are `periods` 2, `half` 1, `length` 27000, `clock_down` false, no fouls, no timeouts (`timeouts` `[0, 0, 0]`), `final_hold` 0, `max_point` 1, `overtime_length` 0, `period_word` `"half"`, `foul_marks` 0, `stop_at_end` false (the clock runs on into added time), `suspensions` 0, `extra_time` false, `stoppage_max` 15 and `cards` true: two halves of 45:00 on a clock that counts up, added time announced in whole minutes, cards and substitutions per player, no extra time and no penalty shoot-out. `cards` says the sport has cards, substitutions, added time and an explicit end of the game. Soccer is scored from the phone only; a console is not supported. Futsal on a console is untested: the decoder has no futsal code. Three fields are for a clock that counts up: `count_up` (true when `clock_down` is false and the sport has a `length`; the server adds it to `game.rules` from the profile, so it cannot disagree with the rules, and the pages read it instead of working it out), `stop_at_end` (a count-up clock stops at the end of its period; false for one that runs on) and `suspensions` (the tenths a suspension lasts, 0 = the sport has none). Handball's (IHF) are `periods` 2, `half` 1, `length` 18000, `clock_down` false, `count_up` true, `stop_at_end` true, no fouls (`foul_marks` 0, `foul_warn` and `foul_bonus` 0), no shot clock, `final_hold` 600, `timeouts` `[2, 2, 0]`, `max_point` 1, `overtime_length` 3000, `period_word` `"half"`, `suspensions` 1200: two halves of 30:00 on a clock that counts up (the second half runs from 30:00 to 60:00), 2-minute suspensions of playing time (they stop with the game clock), two timeout marks per team per half (the IHF gives three per match and at most two per half; the program shows two per half and does not enforce the three), extra time in periods of 5:00 (the clock goes on from 60:00). The period starts and ends are never stored: the start of period `p` is the sum of the lengths of the periods before it, its end is its start plus its length, with `length` the scorer's period length (`score.length`) and `overtime_length` for an overtime. Handball on a console is untested: the decoder reads handball frames, but no recorded game has passed a test yet. Volleyball's are `periods`, `half`, `length`, `final_hold` 0, `timeouts` `[2, 2, 2]`, `scoring` `"sets"`, 25, 15, 3, 2. An unknown or empty `game.sport` gets basketball's rules. A state without `game.rules` (a fixture, an older state) draws with those same basketball values. Fields are added over time; a page treats a missing field as basketball's value.
- `game.overlay` is a copy of `settings.overlay`, the club's on-air setup (Definições > Aparência no ar):
  - `style`: the look, `classico` (default), `lombada`, `cor`, `placa` or `pavilhao`. The overlay puts it on `<html data-style>`; each look other than Clássico is a stylesheet in `web/overlay/styles/`, scoped to its name, that never moves or resizes a box, except the corner scoreboard of Placa and of Pavilhão (see "Placa's scoreboard" and "Pavilhão's scoreboard" below).
  - `bug_position`: `top-left` (default), `top-center`, `top-right`, `bottom-left`, `bottom-center` or `bottom-right`. `lower_third`: `left` (default), `center` or `right`. `margin`: px from the frame's edge, 32 to 96 (default 64). `scale`: percent, 85 to 125 (default 100), for the bug and the lower third.
  - `accent`: `gold` (default), `white`, `orange`, `lime` or `cyan`; it sets `--gold`, which lights the bonus, the points just scored and a running-out shot clock. `away_color`: `own` (the opponent's colour, default) or `neutral` (grey).
  - `hide`: what stays off air, any of `fouls`, `shot` (the shot clock) and `strip` (the sponsor strip on the full screens), on `<html data-hide>`. A sport without fouls or a shot clock will use the same switches. The bug is a row of cells, so a hidden cell closes up; with no shot clock (hidden, or blank as in overtime) the clock centres in its cell.
  - `photo`: the hall photo behind the full screens, a `/media/` URL, or `""` for the stand-in.
  - The overlay takes each of these from the query too (`?style= ?bug= ?lt= ?margin= ?scale= ?accent= ?away=neutral ?hide=fouls,shot`), over the state, for previews and tests; the panel's preview (`?painel=1`) also takes them posted as `{look: "<query>"}`, and `?rodape=1` adds a sample lower third.
  - Anything outside these values is saved as the default. `sponsor_corner` (default true) and `sponsor_every` (minutes, 1 to 30, default 4) drive the sponsor corner (see "Live touches"). `back_line` is the line under VOLTAMOS JÁ (`""` = none).
- `game.credit` is a copy of `settings.credit` (see "Credit").

### Score input (added by Go)
- `internal/source` holds the inputs. A `Source` has a `Name()` (its `settings.input` value) and `Run(stop, out, connected)`: it sends console values with `out` and whether it is connected with `connected` until `stop` closes. `source.Switch` runs one source at a time; `Use(name)` stops the one running, sets `input` in the live state (with `box.connected` false until the new source says otherwise) and starts the new one through `safely`. Values or a connected word from a source already swapped out are dropped. Every value set also goes to `dados/score/*.txt`.
- Console values are a flat map of strings, the keys `state.Machine.ApplyConsole` reads: `home_name`, `away_name`, `home`, `away`, `clock` (`"MM:SS"`, or `"S.T"` under a minute; a clock counting down shows a second until all of it has gone, so 9:59.5 left is `"10:00"`), `period` (`"1"`, `"5"` for the first overtime), `home_fouls`, `away_fouls`, `home_timeouts`, `away_timeouts`, `shot_clock` (`""` when off), `sport` and `box_type`; the phone scorer's frame also sends `period_end` (where the period ends on a clock counting up, in tenths, `""` for a countdown and a sets sport; a console frame has none, and the state machine then works it out from the sport's rules) and `suspensions` (`"[]"` when none, else a JSON list `[{"team":"home","id":1,"number":"7","left":"01:23"}]`, home first, only suspensions with time left; bad JSON reads as none and never fails the frame; more than six entries, or an entry whose team is not `home` or `away`, are dropped); a clock counting up is sent as `"MM:SS"` with the seconds floored (`"00:12"`, `"30:00"`); a sport with cards (soccer) also sends `over` (`"1"` or `""`), `stoppage`, `cards` and `subs` (JSON lists as in `live.cards` and `live.subs`, `"[]"` when none; basketball's and the other sports' frames carry none of these four keys); for a sets sport also `home_sets`, `away_sets`, `serve` (`"home"`, `"away"` or `""`) and `sets`, the phone scorer's finished sets as `"25-20h,18-25a"` (home-away points, then the winner's side `h` or `a`; the letter may be missing). A missing key reads as `""` or 0. Every period, screen and final rule above runs on these values, whatever the source.
- `console` is the box: frames from the Bluetooth reader, decoded by `ble.Decode` into one map kept across frames, and written to `dados/raw.log`. The reader runs whatever the input, so the Caixa tab works and the box stays linked while `manual` is on; the box's frames are dropped meanwhile and the console starts again from its next frame.
- `manual` is the score kept by hand on the scorer's page (`/marcar`, below). It keeps home, away, the period (from 1), the clock in tenths with its own 100 ms tick while it runs (it stops at 0), the period length (default 10:00), fouls and timeouts per team, and an undo of the last 50 actions. It sends its values on every change, every tenth the clock text changes, and once a second besides, as the box does. The Go API: `Do(Action)` with `{ "do", "team", "n", "tenths" }`, `Heartbeat()`, `Score()`, `Seed(live)` and `Restore(score)`. `do` is one of:
  - `point` (`n` from -3 to 3, not 0, and at most `game.rules.max_point` either way: 3 in basketball, 1 in futsal and volleyball, where a larger `n` answers `manual.um_ponto`), `foul` (refused with `manual.sem_faltas` where `game.rules.foul_marks` is 0, as in handball and volleyball) and `timeout` (`n` 1 or -1) for `team` `home` or `away`, never below 0;
  - `clock_start`, `clock_stop`, `clock_set` (`tenths` from 0 to 99:59; a running clock keeps running);
  - `clock_add` (`tenths` more or less on the clock, not 0, kept between 0 and 99:59);
  - `period_next` (the clock stopped at the period length, or at `game.rules.overtime_length` in an overtime when the sport sets one, so basketball's overtime starts at 5:00; team fouls at 0 when `game.rules.fouls_reset`, except that futsal's carry into extra time (`fouls_carry`); timeouts back to 0 where the profile says so, in basketball period 3 and each overtime, 5 on, the FIBA halves), `period_back` (down to 1, the clock stopped where it is), `period_length` (`tenths` above 0; a clock stopped at the old length moves to the new one);
  - `serve` (`team`: the serve to that side) and `set_next`, for a sets sport only: `set_next` is refused (`manual.set_por_acabar`) until `sport.SetWon` says a side has the set, and refused once a side has `sets_to_win` sets (`manual.jogo_acabou`); otherwise it appends the score to the finished sets, puts the points and timeouts at 0 and the serve at nobody, and starts the next set (`period` = sets finished + 1). It is a scorer's tap, never automatic, so a mis-tap at 25-23 never ends a set on air;
  - in a sets sport `point` takes only `n` 1 or -1 (anything else is an error), and +1 also gives the serve to that team (a -1 correction leaves it); `foul` is refused (`manual.sem_faltas`); the clock actions, `period_next`, `period_back` and `period_length` are refused (`manual.sem_relogio`); timeouts are 2 per team per set, back to 0 at each new set;
  - `new_game` (0-0, period 1, the length kept; a count-up clock at 0, suspensions cleared);
  - a count-up clock (`game.rules.count_up`, handball) shows the time played in the game: it starts at 0, `period_next` puts it at the time already played (handball's second half at 30:00, with `period_length` 25:00 at 25:00), it stops at the end of its period when `stop_at_end` and does not start there, `clock_set` and `clock_add` keep it between the period's start and end (a running clock keeps running), `period_back` puts it stopped at the end of the period before, and `period_length` moves a stopped clock sitting at the period's start to the new start;
  - `suspension` (`team`): starts a suspension of `game.rules.suspensions` tenths in the team's first free slot, ending at the game clock plus that, so it stops when the clock stops and carries into the second half; three per team at most (`manual.exclusao_cheia`); a sport with `suspensions` 0 answers `manual.exclusao_modalidade`. `suspension_number` (`id`, `number`: 1 to 3 digits, or `""` to clear it; `manual.exclusao_numero` otherwise) and `suspension_end` (`id`: ends it early) answer `manual.exclusao_desconhecida` for an ID that is not running. IDs count up from 1 within a game (`next_susp` in `manual.json` is the last one given out). Undo takes all three back like any action; a suspension whose time has run out is dropped from the score; the time left rounds up, so the last second reads `00:01`; `manual.json` is read back with every suspension slot checked (an ID outside 1 to 1000000 drops the slot, a bad number is cleared, an end is clamped, `next_susp` is kept between the highest ID held and 1000000);
  - `card` (`team`, `number`: 1 to 3 digits, written without leading zeros; `kind` `"yellow"` or `"red"`): a yellow to a player who already has one is stored as `second_yellow`; a card for a player already sent off (`red` or `second_yellow`) answers `manual.ja_expulso`; a bad kind, team or number answers `manual.cartao`. `sub` (`team`, `out`, `in`: shirt numbers 1 to 99, different) answers `manual.substituicao` otherwise. `stoppage` (`n` from 0 to `game.rules.stoppage_max`) sets the added minutes for this half (`manual.compensacao` outside that); `period_next` and `period_back` put it back to 0. `game_end` is for the last half only (`manual.fim_cedo` before): it sets `over` and stops the clock; `clock_start`, `period_back` or an undo take it back. `card`, `sub`, `stoppage` and `game_end` answer `manual.sem_cartoes` where `game.rules.cards` is false. Where `game.rules.extra_time` is false, `period_next` past the last regulation period answers `manual.sem_prolongamento`. Every card and substitution keeps its minute, written when it was entered. A game holds at most 100 of each (`manual.cartoes_cheios`, `manual.substituicoes_cheias`). `new_game` clears them, the added time and `over`.
  - `undo`: takes back the last action, the clock included only when that action set it (and then stopped). Clock start and stop are never undone, nor is an action that changed nothing.
  A bad action returns a pt-PT error and changes nothing.
- `manual` counts as connected (`box.connected`) while the page called `Heartbeat` or `Do` in the last 60 s. Its frames never connect it by themselves. The panel then shows a "Marcação manual" chip ("Ligado" or "À espera do telemóvel") in place of the box chip, and the Caixa tab takes the box as linked when `box.scan.address` is set.
- `dados/manual.json` holds the manual score (`{ "home", "away", "period", "clock", "running", "length", "home_fouls", "away_fouls", "home_timeouts", "away_timeouts", "sets", "serve", "home_susp", "away_susp", "next_susp", "cards", "stoppage", "over", "next_id", "subs" }`, clock and length in tenths (`home_susp` and `away_susp` are fixed lists of three `{ "id", "number", "end" }`, an empty slot with `id` 0 and `end` a point on the game clock in tenths); `sets` is a fixed list of five `{ "home", "away", "winner" }`, the finished ones first and empty slots with no `winner`; `cards` is a list of `{ "id", "team", "number", "kind", "minute" }` and `subs` of `{ "id", "team", "out", "in", "minute" }`, both `null` until the first one, entries that make no sense and any past the hundredth are dropped at start; `next_id` is the last ID given out, so a restart goes on above an undone card), written after each change and each second the clock runs. It is read at start with the clock stopped, so the time the program was off does not count; the undo starts empty.
- When `manual` takes over from `console` while the program runs, it starts from the live score (score, period, clock, fouls) if the console sent a period, and keeps its own game otherwise. For a sets sport it takes `live.home_sets`/`away_sets`, `live.serve` and the points, fills the finished sets with 0-0 entries (home's wins first, each with its winner) and sets the period to sets won + 1; a console that sent no sets, points or serve leaves its own game. Not during the demo, whose score is invented.

### Scorer's page (`/marcar`, added by Go and the page)
- `GET /marcar` is the page, public like `/painel`, for a phone held sideways (held upright it asks to be turned). The program draws its address on the club's network as a QR code at `GET /marcar/qr.svg` (404 when the PC has no network address); the panel's Marcação tab shows it with the address when phone access is on.
- `GET /api/marcar` → `{ "input": "console" | "manual", "score": <the manual score, as in dados/manual.json>, "undo": <the action undo takes back next, or null> }`. With `input` `manual` it also counts as the page calling in (`Heartbeat`); the page calls it every 15 s.
- `POST /api/marcar` with one action (`{ "do", "team", "n", "tenths" }`, as above) → the same shape after it. `{ "do": "take" }` saves `settings.input` as `manual` and switches the input, starting from the score on air, with the clock running when the console's clock moved in the last 2 s, so a phone can take over from a console that fails mid-game; with `manual` already on air it changes nothing. Any other action while the console is on air answers 409 and changes nothing, so a stray tap never takes the scoring. A bad action answers 400 with the reason and changes nothing. 503 when the program has no manual source.
- Both need the PIN from another device, like every `/api/*` (cookie `pin` or `X-PIN`); the page asks for it on a 401, sets the cookie and retries.
- The page reads the teams, their colours (`game.theme.red`/`on-red` for the club, `game.away.color` for the visitor, with Soalho claro or Marcador text by contrast) and the live score from `/api/events`. It has three columns: the club on the left in its colour, the Marcador strip in the middle, the visitor on the right, mirrored to the right edge. Each team's column holds, top to bottom and in every sport, its name in full, the score, the score buttons, a band of records under a rule (labelled, plain text, never shaped like buttons), and a row of outlined actions; the sport decides which records and actions fill those slots. The page fits a phone on its side (844 × 390) without scrolling; when space runs short the score and the clock tile give up height, never a button. The strip holds, top to bottom: the live dot with "A marcar daqui" (green; Lâmpada with "No ar: a consola" before the take, hollow while the connection is lost), the period button, the clock tile, the undo row and the big Iniciar/Parar. Until `input` is `manual` it shows what the console sends, with every control off but "Marcar daqui", and the long-press tip in place of undo. Then:
  - +1, +2, +3 per team (just +1 where `game.rules.max_point` is 1, decided from the profile and never from the sport's id), and "+ Falta" and "+ Desconto" under the records; a long press (550 ms) on any score, foul or timeout button sends the same action with `n` negative. A tap shows its "+N" at once and is ignored if repeated while it is on its way; the phone vibrates when the program took it, and a failed tap says what was not sent.
  - The period button shows the period on now with a "›" ("2.º período", "2.ª parte", "Prolongamento") and opens the period sheet: the next period ("Período seguinte", or soccer's "Parte seguinte"), "Período anterior" (off in the first period) and the period's length in steps of 1 min (`period_length`, from 1:00 to 99:59; each step applies at once). In an overtime of a sport with `game.rules.overtime_length` the sheet shows that length and the steps are off, since they only set the regulation length.
  - Iniciar/Parar starts and stops the clock. At 0:00 the button waits 2 s, then offers "Período seguinte" (outlined, unlike Iniciar). Changing the period, by that button or the sheet, asks first, since it zeroes the team fouls.
  - The clock tile shows the clock in Soalho while it runs and in Lâmpada while it is stopped, with a pencil in its top corner; the time keeps at least 8 px clear of it and shrinks only when the tile is too short. A tap opens steps of 1 min, 10 s and 1 s (`clock_add`) in two rows, minus above plus, one unit per column, and "Repor" for the period length, a light outlined button beside the time at the top of the sheet, away from "Feito" (bottom right), since a mis-tap there throws the time away. Each step applies at once, so a running clock never jumps back by the time spent choosing.
  - The undo row (the strip's full width) names the action the program would take back (`undo` in the reply) and the team in full ("Anular falta · Visitante"), whoever tapped it. A label too long for one line keeps its size and puts the team on a second line, and the row (46 px at least) grows to fit; a team name too long for that line is cut. With nothing to undo the row says "Anular" and is off.
  - Records per team: fouls as a numeral, which from `game.rules.foul_warn` sits in ink on a gold pill (the bonus chip's gold, with no word) and, from `foul_bonus`, a gold chip with the penalty word ("Bónus", or futsal's "Livre"); a sport with `foul_marks` 0 has no fouls record or "+ Falta". Timeouts as what is left of the allowance in `game.rules.timeouts` ("2 restam", "1 resta", "0 restam"); where the allowance is 0 there is no timeouts record or "+ Desconto" (the scorer still counts a timeout tap there). In basketball: timeouts 2 in the first half, 3 in the second, 1 per overtime, and period 5 is "Prolongamento". In futsal: one timeout per half, none in extra time, "1.ª parte" and "2.ª parte", and period 3 is "Prolongamento". "Repor" on the clock sets the length of the period on now, so it gives an overtime its `overtime_length`.
  - When the game's sport changes (the escalão of the game is changed to one of another sport), `SyncGame` sets the scorer's period length to the new sport's `length` through `Manual.SetLength`, but only for a fresh game (period 1, 0-0, no set played, the clock stopped; it also clears any suspensions); a clock at the old length moves with it, and a game under way keeps its length until the volunteer starts a new one. An empty sport counts as basketball. It does not count as the phone calling in, and the first sync after a start only records the sport, so a length the volunteer set survives a restart. The one exception is a start with no `dados/manual.json`: the scorer has never been used, so that first sync treats it as basketball's and moves a fresh score to the game's sport (a futsal club starts on 20:00, a handball one at 0:00 with 30:00 halves).
  - A count-up sport (`game.rules.count_up`, handball): the clock shows `MM:SS` played (`ClockTextUp`); "Período seguinte" waits for the period's end (the live clock at or past the end the page works out from `game.rules` and `score.length`: the sum of the lengths of the periods before, plus the period's own) and "Repor" sets the period's start (second half: 30:00). With `game.rules.suspensions` above 0 the records band shows "Exclusões" with one chip per running suspension showing the time left over a band with the number, the band filled the same on every chip and empty until the scorer adds one, three a side on one row and the actions hold "+ Exclusão" (`suspension`), each record over its own button (the visitor's band and buttons mirrored: "Exclusões" at the outer edge, "Descontos" by the strip); tapping a chip opens a number field (`suspension_number`, saved with "Feito") and "Acabou" (`suspension_end`).
  - A sets sport (`game.rules.scoring` `"sets"`): one +1 per team, no fouls, no clock and no period button. The tile says "Set n" with the finished sets as small scores under it and what the set still needs. The records band shows the sets won and the timeouts left (`game.rules.timeouts[0]` in every set); the actions hold the serve mark (a ring, filled on the serving side) that sends `serve` for that team, and "+ Desconto". "Set seguinte" takes Iniciar's place; it is enabled, and lit, only when the points win the set by the same rule as `sport.SetWon` (and no side has won the match); it asks "Acabar o set n com casa-fora?" and sends `set_next`.
  - With `game.rules.cards` (soccer): one +1 per team. The records band shows "Cartões", one chip per booked shirt number in the colour of its latest card (a second yellow half yellow, half red), or 0, and "Substituições", the count then the last pair (↓ the player off, ↑ the player on). The actions are "Cartão", which asks yellow or red and then the player's shirt number (the home team's from `game.squad` as big buttons, plus "Outro número" for any other; the other team's by typing it) and sends `card`, and "Substituição", which asks "Sai", then "Entra", and sends `sub`. The added time shows as plain "+3'" under the clock once it is above 0; its stepper (0 to 15, `stoppage`) sits with the clock's steps behind the tile. The clock button stays Iniciar/Parar: the clock runs on past 45:00 and 90:00. The period sheet offers "Parte seguinte" in the first half and, in the last, "Fim do jogo" in its place, behind a confirmation. After "Fim do jogo" that button waits disabled until it is undone or the clock starts again.
  - A visitor with no colour, or one close to the club's, gets Soalho claro, so the two columns never look alike.

- The demo is not a source. It stays in `internal/state` and plays over whichever source runs: the source's values are ignored while it plays, and the timeline, the period saves and the history stay muted as before. It plays the game's sport (`sport.Get` of the game's `sport`), one scripted game per sport, sped up. It feeds the state machine the same frame keys the manual scorer sends. Basketball: four 10:00 periods with a shot clock, overtime on a tie. Futsal: two 20:00 countdown halves, fouls reset at the half, a foul run past 5 to show the free kick. Handball: count-up 2×30:00 with suspensions running (two at once in the second half). Volleyball: sets to 25 with the serve, the match ending 3-1. Soccer: count-up 2×45:00 that runs on, added time of 3 minutes, a yellow and a red card and two substitutions, ended by `over`. If the game's sport changes while the demo runs, the next game is that sport's.

- PIN: only `/api/*` (`/api/events` included) needs the PIN, and only from other devices; requests from the PC itself (loopback) never do. Other devices need it even after `phone_access` is turned off, until the restart that stops listening on the LAN. A wrong PIN costs 1 s, one at a time. `phone_access` takes effect the next time the program starts. `PUT /api/settings` refuses `phone_access: true` without a 4-digit `pin` (400).

- Linking an FPB player that another local player already has (`…/link`, `…/from-fpb`) → 400 with the other player's name.
- Groups also carry `players` and `sponsors` in `GET /api/groups`. `fpb_team_id` is a number, `0` = not linked. `PUT /api/groups/:id` accepts any subset of `name`, `coach`, `fpb_team_id`, `fpb_team_name`, `sport`. Every group carries `sport`, an id from `club.Sports`: filled from `settings.club.sport` on load for groups saved without one, and for new escalões. `sport` takes active sports only (400 `api.escalao.desporto` otherwise). After the link change in the same request, a group that stays linked to an FPB team while its sport is not basketball is refused with 400 `api.escalao.desporto_fpb`, so one PUT can unlink and change the sport. Escalão names can repeat across sports; the panel then shows "Name · Sport".

- `POST /api/game/opponent-logo` returns `{ "crest_url", "color" }` (`color` picked from the logo, `#5C6170` for SVG/WebP) and does not change the game. The picked colour is the logo's most common saturated colour; when that one is too light for white text (gold, yellow), a colour at least a quarter as common that already passes 4.5:1 wins (Atlético Vale: purple, not a darkened gold), else the main one is darkened. On `PUT /api/game`, an empty `away.color` is picked from the crest file in `dados/media` (or the FPB logo it downloads); any colour sent is darkened until white text passes 4.5:1. With `fpb_game_id` set and the FPB game found, the opponent is the side whose `id` is not the escalão's team (home when the club plays away), and an empty `away.name` is filled in capitals by one rule (`opponentName` in `internal/web/game.go`, which holds the word list): the full name when it fits in 12 characters; else the name without the club words BASKET, BASQUETEBOL, BASQUETE, CLUBE, CLUB, GRUPO, DESPORTIVO, ASSOCIAÇÃO, ACADEMIA, the joiners DE, DA, DO, DOS, DAS, E and the abbreviations CB, CD, AD, GD, SC, FC, AC (ignoring case and accents) when something is left and it fits in 20; else the full name when it fits in 20; else the `short_name`; else the name without the club words (or the full name) cut at a space within 20. "Atlético do Vale" → "ATLÉTICO VALE"; "Grupo Desportivo da Ponte Velha" → "GRUPO PONTE VELHA". The panel's FPB picker sends `away.name: ""` and shows the name the server returns, so both always agree. The club's own name never goes through this rule (the home side comes from `settings.club.name`).
- `POST /api/screen` returns `{ "ok": true }`, plus `"obs_error"` when OBS is enabled and the scene switch failed (the overlay screen still changes). `auto` is optional and is saved as `settings.auto_screens`.
- `POST /api/lower-third` with `player_id` → 404 when the player is not in the game's group. `last_name` is everything after the first word of `display_name`.
- `/media/*` is sent with `Content-Security-Policy: script-src 'none'` and `X-Content-Type-Options: nosniff` (logos and photos come from outside).
- `dados/jogos/<date>-<group>.json` is rewritten each time a period is recorded (not in demo): `{ "saved_at", "game", "periods", "sets", "final": { "home", "away" } }`; `sets` is the state's finished sets, and in a sets sport `final` is the sets won (`live.home_sets`, `live.away_sets`). It is rewritten when a set is recorded or dropped too. `<date>` is the first 10 characters of `game.start`, else today.
- Bluetooth discovery (`box.scan` in the live state, for the panel; the overlay ignores it): `bluetooth` is `ok`, `off` (a scan failed, usually the radio is switched off) or `unavailable` (the adapter could not start; retried every 10 s). `message` is pt-PT for the volunteer; after two 15 s rounds that hear no device at all it says so ("Não vejo nenhum dispositivo Bluetooth…") while `bluetooth` stays `ok`. `address`/`name` are the box connected now (empty otherwise), `saved` is `settings.box_address`.
- A device is a likely box when its name, trimmed and lower-cased, contains `stramatel`, `livestream` or `live stream`, or it advertises service `a002`. With no saved address the reader connects to the strongest likely box; one that turns out not to have service `a002` + characteristic `c305` is skipped until "Esquecer caixa".
- `settings.box_address` (string, `""` by default) is the address from the last good connection (a MAC on Windows, a UUID on macOS). When set, the reader connects to it directly, then scans for it. `PUT /api/settings` never changes it.
- `GET /api/ble/devices` → devices heard in the last 60 s, likely first, then strongest signal: `[ { "address", "name", "name_quoted", "rssi", "services": ["a002"], "likely", "last_seen" } ]`. `name` is raw (`""` when the device sends none); `name_quoted` is the Go-quoted name so leading spaces show. `[]` in demo mode.
- `POST /api/ble/try` `{ "address" }` stops the scan and connects (15 s limit). `200 { "ok": true }` when it is the box (saved, frames start); `200 { "ok": false, "error": "Este dispositivo não é a caixa (não tem o serviço do marcador)." }` (or another pt-PT reason) otherwise, and scanning resumes. 400 without an address, 503 in demo mode.
- `POST /api/ble/forget` clears `box_address`, drops the link and goes back to discovery. `200 { "ok": true }`.
- `POST /api/system/bluetooth-settings` opens the PC's Bluetooth settings (Windows `ms-settings:bluetooth`, macOS System Settings). `501 { "error" }` elsewhere.
- `GET /api/ble/capture` → the console recording's state: `{ "on", "file", "bytes", "frames", "dropped", "max", "stopped" }`. `file` is the newest recording's name (`""` before the first), `bytes` and `frames` what is written so far, `dropped` the frames the writer was too slow for, `max` the size cap in bytes (50 MB). `stopped` says why the newest recording ended: `""` while it runs, then `off` (the switch), `cap`, `box` (the box disconnected) or `error` (the disk's message goes to `marcador.log`, never into the reply, since it names folders). In demo mode, and with no reader, it answers `on: false`.
- `POST /api/ble/capture` `{ "on": true|false }` is the panel's "Gravar a consola" switch, off at every start; it answers the same shape. On needs the box linked (409 otherwise, also when the link drops while the file is being made), a reader (503 in demo mode) and room: 409 with the folder's own message when `dados/captura/` holds more than 300 MB, until the volunteer sends or deletes old files. Disk errors answer 500 with a generic message, the detail in `marcador.log`; off with nothing recording is not an error. Both go through `ServeHTTP`'s Host, Origin and PIN checks like every route.
- `POST /api/system/capture-folder` opens `dados/captura/` in the PC's file manager (made first if missing). Only from the PC itself (403), 501 where the program has no file manager to call.
- `dados/bluetooth.log`: one line per device at most every 30 s while scanning: time, address, quoted name, `rssi=`, `services=`, `likely=`.
- Player photos (from the FPB roster's `photo_url`; there is no manual upload):
  - Players also carry `photo_url` (the local copy, `/media/pl-<player id>-<content hash>.<ext>`, so a new photo gets a new address, or `""`) and `photo_source` (the FPB address it came from, `""` when none).
  - `POST …/players/import` sets `photo_source` on linked players from the roster; a new photo alone does not put a player in `updated`. Suggestions carry `photo_url` (the FPB address, for the panel to preview). The response also has `photo_errors` (int, downloads that failed or were not tried).
  - `POST …/:pid/link` and `POST …/from-fpb` accept `photo_url` (the suggestion's FPB address) and reply with the player after the download.
  - After import, link and from-fpb the server downloads the photo of every player whose `photo_source` changed or who has a `photo_source` but no `photo_url` (so a failed download retries on the next import). Only `https://` on `sav2.fpb.pt` or `www.fpb.pt` is fetched, redirects included (15 s limit, 5 MB). Failures are logged and leave `photo_url` empty. The downloads of one escalão stop once 3 in a row cannot reach the host or time out (a missing photo or a refused redirect is an answer and does not count), and at the 10 minutes a setup or update may take, a download under way included; the photos not tried stay empty and count as failures.
  - Unlinking (`DELETE …/link`) clears `photo_url` and `photo_source` and deletes the file; deleting a player or a group deletes their photo files.
  - Live state: `game.squad[].photo_url`, `lower_third.photo_url` (jogador only) and `game.photos` (copy of `settings.photos`). The overlay shows the photos only when the matching switch is on; a squad member without a photo shows initials, a lower third without one uses the layout without a photo.
- Command line (for development): `-demo` starts the demo and skips Bluetooth; `-nobrowser` does not open the panel; `-replay <file>` plays a console capture with no Bluetooth ("Console capture").
- Club setup (first run). It needs `settings.club_search`, the club's name on the FPB ("Clube Exemplo", typed in Definições > Clube as "Nome do clube na FPB"); while it is empty the setup never runs by itself and the daily update skips the club's team list. With `club_search` set, no escalões and `settings.club_setup` empty, the program sets `club_setup` to `"pending"` and, in the background, searches FPB `/api/teams?name=<club_search>`. It keeps the club's teams (name, without accents and case, starting with `club_search` the same way) and creates one linked escalão per team, with every roster player added (auto-accepted suggestions) and their photos. On success `club_setup` becomes the time it finished and the setup never runs again by itself; while it stays `"pending"` (FPB unreachable) every start retries. Never in `-demo`.
  - Escalão name: `age` + `gender` ("Sub 14 Feminino"); a Sub-N in `squad_label` that differs from `age` replaces it ("Sub-21 M" on a Sénior team → "Sub 21 Masculino"); a team name ending in "-B" or " B" adds " B". Order: teams with fixtures first, then Sénior, Sub 21…14, Mini 12…8, Masculino before Feminino. Of two teams with the same name the first in that order keeps it; the other gets " (2)" and goes last.
  - The setup adds no coach and no sponsors: the club types those in the panel.
  - `…/link` and `…/from-fpb` accept `fpb_athlete_id` (the suggestion's; the panel sends it) and save it on the player.
  - `POST /api/club/setup` runs the same setup now and waits: `200 { "created", "imported_players", "errors": ["…"] }`. Teams already linked are skipped; an unlinked escalão with the same name is linked instead of creating another; names and coaches already there never change. `400` while `club_search` is empty; `409` while a setup or daily update runs; `502` when the FPB can't be reached. The panel shows the button "Importar equipas do clube" in Plantel while no escalão is linked.
  - `GET /api/status` also returns `"club_setup": { "running", "done", "total" }` (`done` = teams finished), so the panel can say "A importar 7 de 14 equipas…".
  - `settings.club_setup` and `settings.club_teams` are kept by `PUT /api/settings`, like `box_address`.
- Daily FPB update. At start (after the club setup) and then every 24 h, and in the background when `PUT /api/game` picks another escalão or FPB game, every linked escalão gets the same auto-accepted import: linked players get the FPB name, photo and (unless typed by hand) number, as in `…/players/import`; new FPB players are added; players missing from the FPB are never deleted. At start an escalão updated in the last hour is skipped. Nothing happens while the FPB can't be reached.
  - Groups carry `last_sync` (RFC 3339, `""` = never) and `last_changes` `{ "new_players", "numbers", "photos", "left", "returned" }` from the last update (the manual import also sets them). The panel shows "Atualizado da FPB há X: 2 jogadores novos, 3 fotos novas."
- New season. FPB makes new team ids each season and `/api/teams` lists only the current one. The daily update acts only when the club teams' slugs end in a season newer than `settings.club_season` (the newest seen, `"2026-2027"`), so an empty or partial answer changes nothing. Then each escalão linked to a club team (it has `fpb_team_key`, or its team is in `settings.club_teams`) whose team left the list is moved to the one new team (not linked elsewhere) with the same escalão name rule (`fpb_team_key`, else the escalão name without " (n)"); of two such teams, the one with the same club name (the part of `fpb_team_name` before " · ") wins. Exactly one → relinked and updated now. None or several → `needs_team: true` and the panel says "A FPB tem uma época nova: escolha a equipa deste escalão" over the FPB picker. Escalões linked by hand to a team outside the club are left alone. New club teams that no escalão has, and that are not one of several candidates, get an escalão as on the first run.
  - `settings.club_teams` holds the club's team ids that are linked to an escalão after each setup or update. A setup left `"pending"` is finished by the daily update once the FPB answers.
  - Groups carry `fpb_team_key` (the name rule applied to the linked team), `needs_team` and `synced_team` (the team at the last update). `PUT /api/groups/:id` accepts `"fpb_team"` (the FPB team object picked: `id`, `name`, `age`, `gender`, `squad_label`), which sets `fpb_team_key` when it is a club team; a new `fpb_team_id` clears `needs_team`. The panel sends `fpb_team_id`, `fpb_team_name` and `fpb_team` only from the FPB picker; "Guardar" sends just `name` and `coach`, so a page loaded before a relink can't undo it.
  - A relinked team whose roster is still empty marks nobody inactive and keeps `synced_team`; the next update with players does it. An update whose escalão changed team while the roster was loading drops that roster.
  - Limits per run: 50 club teams, 100 players per roster, about 10 minutes (a setup cut short is not marked done).
  - Players carry `fpb_athlete_id`; imports find a linked player by `fpb_player_id`, else by `fpb_athlete_id` (and take the new player id), so returning players keep their photo. Suggestions carry `fpb_athlete_id` too.
  - Players carry `inactive` (bool). The first update after the escalão moved to another team sets it on linked players missing from the new squad; any import clears it when the player is back. `PUT …/players/:pid` accepts `inactive` ("Voltar a mostrar"). Inactive players are left out of `game.squad` in the live state; the panel hides them from "Plantel do dia" and the lower-third buttons and lists them under "Já não estão na equipa" in Plantel.

### Squads and fixtures without the FPB (added by Go and the panel)
- `POST /api/groups/{id}/players/csv` multipart (`file`, a CSV up to 1 MB) adds a squad: `number,name,photo` per line, `,` or `;` (Portuguese Excel), UTF-8 or Windows-1252, an optional header whose first field names the number column (`numero`, `nº`, `number`…), blank lines skipped. The number may be empty or 0-999; `photo`, optional, is an `http(s)` address. A line whose name matches a player (case and accents ignored) updates that player's number (and clears `number_from_fpb`) and, for a player not linked to the FPB and without a photo given by hand, the photo address; the other lines are new players; nobody is removed. → `{ "added", "updated", "skipped": [{ "line", "reason" }], "players" }`. Photo addresses download in the background into `dados/media/pl-<id>-<hash>.<ext>` (any host, unlike the FPB's photos).
- `POST /api/groups/{id}/players/{pid}/photo` multipart (an image) sets the player's photo and `photo_by_hand: true`; `DELETE` removes it. A photo given by hand stays through FPB imports, links and unlinks and CSV imports.
- `group.fixtures` are the escalão's games kept by hand: `{ "id", "start" (RFC 3339), "opponent": { "name", "short", "color", "crest_url" }, "home" (the club plays at home), "venue", "competition", "round" }`, in date order. `GET/POST /api/groups/{id}/fixtures`, `PUT/DELETE /api/groups/{id}/fixtures/{fid}`; a fixture needs a start and an opponent name, a sigla of at most 4 letters (saved in capitals), and a colour as `#RRGGBB` (else `""`, the crest's). `PUT` keeps `crest_url`, which `POST …/fixtures/{fid}/crest` (multipart image) sets, picking the colour from it when none was typed; deleting the fixture deletes an upload nothing else uses.
- `POST /api/groups/{id}/fixtures/csv` multipart adds `data,hora,adversario,casa_fora,local,competicao,jornada` lines: the date as `20/12/2026` or `2026-12-20`, the time as `18:30` or `18h30` (the club's time zone), `casa`/`fora` (also C/F, home/away; empty = casa), the rest optional. → `{ "added", "skipped", "fixtures" }`.
- `group.calendar_url` is the escalão's calendar link: an iCalendar (`.ics`) feed over `https`, `http` or `webcal` (TeamSnap, SportsEngine, GameChanger, federations, a club's own calendar). `PUT /api/groups/{id}` `{ "calendar_url" }` saves it (`""` clears it; 400 for another scheme or no host) and refreshes the next game when the escalão is the game's. The feed is fetched at most once a day into `dados/cache/ics/` (4 MB at most, and it must start like a calendar); when the link fails, the last copy answers. Each VEVENT with a start becomes a game, ref `ics/<UID>`: a UTC start as is, a `TZID` Go knows in that zone, a floating one in the club's zone, and an all-day one untimed (never picked). Recurring (`RRULE`) and cancelled events are skipped. The opponent and home/away come from SUMMARY by the club's `name` or `short`: "Club vs Rival", "Club - Rival", "Club x Rival" (first team at home), "Rival @ Club", "Club at Rival", and the team apps' "vs Rival" / "at Rival"; a title with neither name is the opponent, at home. LOCATION is the venue.
- `GET /api/groups/{id}/calendar` → the link's timed games shaped like `fixtures` (`id` `ics/<UID>`, `start`, `home`, `opponent.name`, `venue`), `[]` with no link, 502 when it can't be read and there is no copy. The Jogo tab lists them with the typed ones, marked "do calendário", to pick but not to delete, and has the link field under the CSV import.
- Panel: Jogo has a "Calendário do escalão" card for every club, with the upcoming fixtures (a click fills the game of the day like an FPB game, with no `fpb_game_id`), a form to add one with an optional crest, a delete per game, and the CSV import with a template to download. Plantel has "Importar CSV" with its template and a summary of the lines left out, and "Foto" / "Tirar foto" per player.

### Próximo jogo and Voltamos já (added by Go, the overlay and the panel)
- `game.next` is the club's game after the one of the day, from every provider of the escalão (`internal/provider`): the FPB's next games of the linked team (`fpb_team_id`, 14 days, the disk copy when offline) where the FPB covers the club, the escalão's own `fixtures` (below) for every club, and its calendar link (`calendar_url`, below), together. A provider that fails only gives the reason when the others have nothing. The game of the day is the entry whose ref is the game's `fpb_game_id`, and the next game is the earliest entry that starts after it (no provider's order is relied on). An entry whose `time` is not "HHhMM" or "HH:MM" can't be placed and is never picked. Without an id, or when the FPB no longer lists it, the game of the day is the entry on ref's day in Lisbon, ref being `game.start` or, when that is earlier, now less 3 h (a game that runs past midnight); the next game is the earliest entry on a later day. So a morning setup or a manual game still skips tonight's game.
- `next.at_home` is true when the club is the home side. `opponent` follows the game's rules: `name` from `opponentName`, `short` FPB's `short_name` when it fits in 4 (else the first 3 letters of `name`), `initials` = `short`, the logo from `dados/media/opp-<FPB id>.<ext>` when it is already there, else downloaded to it (`crest_url: null` when that fails) and `color` picked from it at 4.5:1. `full_name` is FPB's name. `start` is RFC 3339 built from FPB `date` + `time` in Europe/Lisbon (Go embeds the zone database for Windows). `venue` is tidied like the game's; `round` is "Jornada N" from `game_week`, else `phase_name`.
- `game.at_home` is the same for the game of the day; `null` when no provider has a game that day. A fixture's `color` and `/media` crest are used as typed; a round that is only a number becomes "Jornada N".
- `game.next` is `null` when there is none, with a short pt-PT reason in `next_note` (no escalão, an escalão with no games from any provider, team unknown to the FPB, FPB unreachable or answering 429 with no copy, no later game, or "A ler os jogos da FPB…" while the game just changed). The panel shows the reason on the disabled "Próximo jogo" button; `POST /api/screen` `{ "screen": "proximo" }` without a next game is refused with 400. The overlay treats `proximo` without `game.next` as `nada`, so it never shows an empty card.
- Go works it out at start and every hour, after each `PUT /api/game`, and after `PUT /api/groups/:id` changes the `fpb_team_id`, `calendar_url` or `sport` of the game's escalão, in the background. A result for a game that changed meanwhile is dropped.
- Overlay: both are full screens on the pavilion backdrop with the lockup and the sponsor strip, and follow the full-screen rules: they wait for the previous screen to fade, and a time-out (`desconto`) replaces them like any full screen. `proximo` keeps the club left (`EM CASA` or `FORA` under its name) and the opponent right, with FPB's full name under the short one when they differ; the date reads "SEXTA 20 NOV" and "21:45" in Lisbon. `voltamos` shows the crest, VOLTAMOS JÁ, `back_line` when set, and a small score bar while a game is going on (`box.connected` and a score above 0 or a recorded period). Its only motion while it holds is a slow opacity and scale breath on a halo behind the crest (opacity only with reduced motion, none with `?anim=0`).
- Fixtures: `proximo-casa`, `proximo-fora`, `proximo-longo`, `voltamos`, `voltamos-sem-jogo` (with `?screen=` of the same name).
- Panel "Miniatura YouTube" (Ecrãs) draws a 1280x720 PNG in the browser from the live state (no server call): lockup, `game.group.name`, both crests (initials when one fails to load; images load with CORS so the canvas is never tainted), both names in Barlow Condensed 800, `EM CASA`/`FORA` from `game.at_home` when known, and weekday, date and time from `game.start` in Lisbon. No sponsors. It shows a preview, then saves `miniatura-<home>-vs-<away>-<YYYY-MM-DD>.png`.

### Time-out squeeze (added by Go and the overlay)
- One definition: `web/overlay/overlay.css` holds the window (`--win-x: 416px; --win-y: 64px; --win-w: 1440px; --win-h: 810px`, overlay px), its time (`--t-squeeze: 900ms`) and its curve (`--ease-in-out`, a `cubic-bezier`). Go reads these four tokens from the embedded file at start (`readSqueeze` in `internal/web/camera.go`); without them the camera does not move and `POST /api/screen` returns the reason in `obs_error`.
- Settings: `obs.camera_source` is the camera input in the program scene; `""` picks the topmost shown DroidCam input (kind or name contains `droidcam`) below the top browser source, else the topmost shown video capture there (`dshow_input`, `av_capture_input*`, `v4l2_input`, `macos-avcapture`). `obs.camera_fit` is `"contain"` (default; the whole picture, bars where the aspect differs) or `"fill"` (covers the canvas, cropping two sides); it applies to full screen. On `desconto` the picture is always contained in the window, centred; the overlay paints its background around it, with a red frame on the picture. `obs.camera_full` is the last full-screen placement with the source size, canvas size and fit it was made for (`{ "x", "y", "w", "h", "crop_left", "crop_right", "crop_top", "crop_bottom", "source_width", "source_height", "canvas_width", "canvas_height", "fit" }`); only the program writes it, `PUT /api/settings` keeps it, and clears it when `camera_source` changes. Any `camera_fit` other than `"fill"` is saved as `"contain"`.
- Mode: with `obs.timeout_scene` set and present in OBS (`GetSceneList`), the old two-scene switch runs. Otherwise the camera moves in the program scene. New settings default `timeout_scene` to `""`.
- Moving: on `desconto` the server reads the canvas (`GetVideoSettings`), the program scene (`GetCurrentProgramScene`) and its items with their transforms and source sizes (`GetSceneItemList`), then tweens the camera from where it is to the window with `SetSceneItemTransform` every 20 ms over `--t-squeeze` on `--ease-in-out` (top-left alignment, `OBS_BOUNDS_NONE`, crop in whole pixels, scale from what is left). Leaving `desconto` tweens back to the full-screen placement. A new move while one runs starts from the current position, with the time cut in proportion to the distance left, so desconto → marcador → desconto never leaves the camera half way. Automatic screen changes move it too.
- A canvas other than 1920x1080 scales the window by canvas/1920 and canvas/1080 (the overlay is assumed to cover the canvas); `state.camera` stays in overlay px.
- Refit: at start and every 4 s while the screen is `marcador` or `nada`, the server checks the camera; when its source size, the canvas or the fit differs from `camera_full`, it puts the camera at the new full-screen placement at once and saves it.
- `GET /api/obs/sources` (no longer used by the panel, which reads `POST /api/obs/cameras`) → `{ "scene", "sources": [ { "name", "kind" } ], "auto": "<name or empty>" }`, the program scene's inputs from the top; 502 `{ "error" }` when OBS can't be reached.
- `POST /api/obs/camera/fit` ("Ajustar câmara") puts the camera at full screen with the saved fit now, whatever its resolution, and saves it: `{ "ok": true, "fit": { "source", "source_width", "source_height", "canvas_width", "canvas_height" }, "warning": "" }`; `warning` asks for a 1920x1080 canvas when OBS has another. 502 `{ "error" }` when OBS or the camera can't be found. The panel saves the settings form first.
- Errors (OBS closed, source missing, no picture yet) never stop the screen change; `POST /api/screen` returns them in `obs_error` and `GET /api/status` in `obs.error`.
- Overlay: with `state.camera` set, or with `?preview=foto`, `desconto` enters by shrinking the window (and the hole in the background with it) from `camera.full` (else the canvas) to `camera.window` (else the CSS window) over `--t-squeeze` on `--ease-in-out`, in step with the camera; the left column follows as it settles. Leaving, the text fades and the window opens back out on the same curve, then the next screen enters. With neither, the old L-shaped entrance plays. With `?preview=foto` the hall photo plays the camera and moves the same way; without `preview` there is no photo.

### OBS set up by the program (added by Go and the panel)
- `POST /api/obs/setup` `{ "camera": "", "old": "" }` is "Configurar OBS" and "Reparar". One at a time (409 while one runs). It first reaches OBS: with `obs.host` on this PC it reads obs-websocket's `config.json` (`%APPDATA%\obs-studio\plugin_config\obs-websocket\config.json`, OBS 30.2 and later) and uses its port and password when the server is on there. If OBS doesn't answer and `obs64.exe` is not running, it turns the server on in that file (`server_enabled`, `auth_required` true, `server_port` 4455, `first_load` false, a random 24-character `server_password` unless one is there; every other key kept; written through a temporary file and a rename), saves host, port and password in `settings.obs`, starts OBS and waits up to a minute for it. If OBS is running it never writes the file: with the server on in the file it waits up to 20 s (OBS may still be starting), else the step fails and says to close OBS or turn the server on by hand. The check, the write and the start happen under one lock, with the start at launch. A broken `config.json` is never rewritten.
- Then it brings OBS to this state, changing only what differs: scene `Hallstream` (created if missing); the overlay browser source (an input whose `url` path is `/overlay` on a port from 8765 to 8775, preferring the name `Hallstream overlay`, else created with that name) with `url` = the overlay on the port the program runs on, `width` 1920, `height` 1080, `reroute_audio` true, `is_local_file` false, in the scene and shown; the camera in the scene and shown; the overlay above the camera; base and output 1920x1080; the program scene set to `Hallstream` (neither while streaming or recording); then the camera fit of `POST /api/obs/camera/fit`, retried for about 8 s while a new camera has no picture yet. It never deletes or changes a user's source other than the overlay's settings.
- Camera: `camera` is a choice value (`"source:<name>"`, `"device:<video_device_id>"`, `"plugin"`) or `""` for `settings.obs.camera_source` (or automatic when that is empty too). Automatic takes a DroidCam source (kind or name contains `droidcam`, or a `dshow_input` whose `video_device_id` contains it), else a video source already in the scene, else the only choice there is. With several it returns `"result": "choose"` on the camera step and `choices`: video sources in OBS (not browser, image, text, colour, screen or audio kinds), the DroidCam OBS plugin (`droidcam_obs`) when installed with no source yet, and the `dshow_input` devices from `GetInputPropertiesListPropertyItems` (`video_device_id`) that no source uses, DroidCam first. Listing devices needs a `dshow_input`: with none, it adds a hidden one and removes it. A device becomes a new `dshow_input` named after it; the plugin becomes `DroidCam`, connected to the first USB device in its `device_list` (`connect` button). A camera that replaces another hides the old one (`old`, the `camera_source` before the panel saved its form; else the saved one) (and any other capture source) in the scene; it stays in OBS. The camera used is saved as `camera_source`.
- Reply: `{ "ok", "ready", "camera", "steps": [ { "id", "label", "result", "detail" } ], "choices": [ { "value", "type", "label", "droidcam" } ] }`. `result` is `ok`, `created`, `fixed`, `failed`, `choose` or `later` (the canvas size or the program scene can't change while OBS streams or records, so the program leaves them; `later` doesn't count as a problem); step ids are `websocket`, `scene`, `overlay`, `camera`, `old-camera`, `order`, `video`, `program`, `fit`. `ready` (and `ok`) is true when nothing failed but the fit. The first ready run sets `obs.launch` true; every ready run sets `obs.setup_at` and `obs.enabled`. 502 `{ "error" }` when the connection drops half way.
- Health check: the same checks without changes, on every new connection to OBS, every 30 s, and after a setup. `GET /api/status` → `obs.health` `{ "checked", "ready", "problems": [ "<detail of each failed step>" ] }`. With a chosen camera, "missing" means that source is gone.
- `POST /api/obs/cameras` → `{ "cameras": [choice] }` for Definições > Câmara (a POST because listing devices may add and remove a hidden source). 502 when OBS can't be reached.
- Other devices (phones, with the PIN) can run Configurar OBS over the WebSocket but never write `config.json` or start OBS. `GET /api/settings` and `PUT /api/settings` answer them with `obs.password` empty, and their `PUT` keeps `obs.host`, `obs.port`, `obs.password`, `obs.launch` and `obs.close_on_exit` as they are. obs-websocket always listens on every network interface (it has no setting for localhost only), so the password is what guards it.
- Stream: `GET /api/obs/stream` → `{ "known", "stream": null | { "active", "reconnecting", "duration_ms" } }`, kept by the server from `GetStreamStatus` every 3 s while connected (`null` when OBS can't be asked). `POST /api/obs/stream/start` checks `GetStreamServiceSettings` first: an `rtmp_custom` server with an empty `key` → 409 "Configure a conta do YouTube no OBS (Definições > Transmissão) uma vez."; else `StartStream` and the new state. A YouTube account linked in OBS (`rtmp_common`) may keep no key there, so it is not checked; when OBS refuses `StartStream` the 502 says to check the account in OBS. OBS can also take `StartStream` and never send (a linked account with no broadcast shows a message on the PC): when the last `GetStreamStatus` that answered still says not active after 30 s (failed reads in between don't count, and inactive reads are not kept meanwhile, so a stale active status can't end the new broadcast), the program sends `StopStream` and answers 502 telling the operator to look at OBS on the laptop, and a YouTube broadcast made for the start is dropped as for a refusal. `POST /api/obs/stream/stop` → `StopStream`. Already live, or already stopped, is not an error. The program never starts the stream by itself; the panel asks before stopping.
- `obs.launch` ("Abrir o OBS com o Hallstream", Windows): at start, with OBS enabled on this PC and `obs64.exe` not running, the program starts OBS from the `HKLM\SOFTWARE\OBS Studio` install folder (64- then 32-bit registry view), else `%ProgramW6432%`/`%ProgramFiles%\obs-studio`, as `bin\64bit\obs64.exe --minimize-to-tray --disable-shutdown-check` with `bin\64bit` as its working folder (OBS finds its files from there). `--disable-shutdown-check` exists in OBS 30 and 31 only. Then it reconnects with growing waits (1 s to 10 s). It never starts a second OBS.
- `obs.close_on_exit` ("Fechar o OBS ao sair", off by default): "Sair" stops a live stream, then sends `WM_CLOSE` (what the window's X sends) to every top-level window of `obs64.exe`, the hidden tray one too, and waits 15 s; OBS is ended by force after that only when the stream is not live. With the stream live, "Sair" asks first in a message box.
- `start_with_windows` ("Abrir com o Windows", off by default): `POST /api/system/autostart` `{ "on" }` puts `Hallstream.lnk` in the user's Startup folder (made like the desktop shortcut) or removes it, and saves the answer. At every start with the switch on, the program puts the shortcut there again, so a backup unzipped on another PC or a moved exe still opens with Windows. Only from the PC itself (403), 501 where the system has none. `PUT /api/settings` keeps it, and keeps `obs.setup_at`. `GET /api/status` → `"autostart": true` when the switch can show, `"obs_app": true` where the program can start OBS.
- Panel: a stream bar at the top of Ecrãs ("Iniciar transmissão" / "Terminar transmissão", the time on air, "Reparar" when the health check finds a problem), "No ar 0:00:00" in the top bar, and the OBS chip ("Pronto", "Precisa de reparação", "Sem ligação"). Off air, the bar reads "Pronto para transmitir" with a green dot when nothing is missing; otherwise "Fora do ar" and "Antes de começar:" with one line per gap, each linking to the tab that fixes it: the box not connected (unless in demo; with `input` `manual` it is the scorer's phone, with no link), no game picked (`group_id` and `away.name` in `GET /api/game`), the OBS health problem or "A verificar o OBS…", and an expired YouTube login. The buttons stay on: the list advises, it doesn't block. Mock states for screenshots: `?mock=1&obs=off|ready|problem|live|nokey|choose`, `&act=setup|start|stop`.

### YouTube (added by Go and the panel)
- The program signs in to the club's channel itself (OBS's own YouTube account can't be driven over obs-websocket). OAuth for installed apps: the club's own "Desktop app" client, a redirect to `http://127.0.0.1:<free port>` on a listener separate from the server, PKCE `S256`, a random `state`, scope `https://www.googleapis.com/auth/youtube`. The listener answers only `GET /` with that Host, ignores a wrong `state` (400, keeps waiting), takes one good answer and closes; it gives up after 5 minutes. `golang.org/x/oauth2` (v0.38.0) does the exchange and the refresh; the API calls are plain REST (`internal/youtube`). Guide for the club: `docs/youtube/SETUP.md` (shipped as `YouTube/LIGAR-YOUTUBE.txt`).
- `dados/youtube.json`: `client_id`, `client_secret`, `token` (refresh token included), `channel`, `stream` (the reusable stream: `id`, `server`, `key`), `expired`. On Windows the whole file is sealed with DPAPI for the Windows user (`DPAPI1:` + `CryptProtectData`, no UI), so another account or a copy of the folder can't read it (a copy needs a new login); elsewhere it is plain JSON at 0600. Temp files (`dados/.tmp-*`) left by a closed program are deleted at start. No endpoint ever returns the secret, the token or the stream key. The login page's text is HTML-escaped.
- `GET /api/youtube` → `{ "setup", "configured", "has_secret", "client_id", "connected", "expired", "channel": null | { "id", "title", "thumbnail" }, "stream_ready", "connecting", "error" }`. `client_id` is `""` for other devices; `setup` is true on the PC itself. `GET /api/status` carries the same object as `youtube`.
- PC only (403 otherwise): `PUT /api/youtube/client` `{ "client_id", "client_secret" }` (the id must end in `.apps.googleusercontent.com`; an empty secret keeps the saved one; 409 while connected with another id), `POST /api/youtube/connect` → `{ "auth_url" }` (the panel opens it; a new connect cancels the one waiting), `POST /api/youtube/disconnect` (revokes the refresh token at Google, then forgets token, channel and stream; the client stays).
- After the login: `channels.list mine`, then the stream: a reusable RTMP `liveStream` titled "Hallstream" (found by title in `liveStreams.list mine`, else inserted with `cdn.resolution`/`frameRate` `variable`), and OBS set to `rtmp_custom` with `server` = `ingestionAddress` and `key` = `streamName` (`SetStreamServiceSettings`, only when it differs and OBS isn't live). Configurar OBS does the same as its last step, `youtube` "Transmissão para o YouTube" (`later` while OBS streams). Without YouTube none of this runs and the stream buttons drive OBS as before.
- `POST /api/obs/stream/start` with YouTube connected, before `StartStream`: the game's key (`fpb:<fpb_game_id>`, else `<group>:<date>:<away name>`) finds the last broadcast made for it; when YouTube still has it `created`, `ready`, `testStarting`, `testing`, `liveStarting` or `live`, it is reused (bound again if needed). Otherwise `liveBroadcasts.insert` (`privacyStatus` public, `selfDeclaredMadeForKids` false, `enableAutoStart`/`enableAutoStop` true, `monitorStream.enableMonitorStream` false, `scheduledStartTime` now) and `bind` to the stream. Title: "Casa vs Atlético Vale · Sénior Masculino · 2ª Divisão Masculina J6" (club first at home, opponent first away when `at_home` is false; names from the scoreboard names, words over 3 letters capitalised; "Jornada N" → "JN"); without `<`/`>`, and over 100 characters it drops the competition, then cuts. Description: competition · round · escalão, venue, and the date in Lisbon ("Domingo, 15 de novembro de 2026, 18:00"). An expired login → 409 with "A ligação ao YouTube expirou…", and OBS doesn't start. Body `{ "test": true }` is "Transmissão de teste": 409 without YouTube connected (OBS would send to the public stream); otherwise the same, with `privacyStatus` private, the title prefixed "Teste · " (cut to 100), the key `teste:<key>` so the game's real start never reuses it, and a record with `test` true. The panel sends no thumbnail for it, and at the stop it stays private (no unlist, not picked up by `RunYouTube`; `POST /api/youtube/unlist` answers 409 for it). A test start while the game is on air, or a game start while a test is, is 409, so the record on air keeps its end.
- `GET /api/obs/stream` (and the start/stop replies) add `youtube`: `null` without YouTube, else `{ "connected", "expired", "live": record|null, "ended": record|null, "waiting", "error" }`.
- `POST /api/youtube/thumbnail` multipart (`broadcast_id` of a record, `file`: PNG, 8 MB at most, else 413): the panel draws the Miniatura YouTube canvas after a start whose `live.thumbnail_set` is false and sends it; the server calls `thumbnails.set`. A 403 (channel not verified for custom thumbnails) → 502 with a message; the stream goes on. Behind the write guard as the fourth multipart upload.
- Stop (`POST /api/obs/stream/stop`, or OBS reporting the stream off): the record on air gets `ended`, `score` and `result` ("Casa 82-76 Atlético Vale"). Then, in the background: a look at the broadcast 30 s later, then 1, 2, 4, 5, 5… minutes apart, 10 looks at most; at `complete`, `videos.list` + `videos.update part=status` with `privacyStatus` unlisted and `embeddable`, `license` and `publicStatsViewable` sent back as they were (YouTube clears status fields left out). Still `live` at the fourth look → one `transition` to `complete`. Never live → `privacy_error` says so. Out of looks → `privacy_error` asks for "Tornar não listado" later. A start of the same game meanwhile stops the waiting. Records still waiting are picked up again at start (`RunYouTube`).
- `POST /api/youtube/unlist` `{ "broadcast_id" }` → `videos.update` now (retry, and "Tornar não listado" in Transmissões). 404 for an id neither in the record nor in the channel list read for Transmissões; 502 with the reason.
- When OBS refuses `StartStream`, the broadcast stays (reused on the next try) but is no longer on air, so a later stop doesn't end it. Connect, Desligar and saving another client id cancel a login still waiting, outside `ytMu` (a login that is finishing takes `ytMu`). A Desligar while the stop waits leaves `privacy_error` saying so, and failed looks say why.
- `dados/transmissoes.json`: `[ { "broadcast_id", "video_id", "title", "group_id", "escalao", "opponent", "date", "score", "result", "privacy", "link", "game_key", "status", "on_air", "ended", "privacy_error", "thumbnail_set", "thumbnail_error", "started_at" } ]`. `started_at` (RFC 3339) is the broadcast's first start; a reused broadcast keeps it.
- `GET /api/youtube/history?escalao=&season=&refresh=1` → `{ "items": [record], "escaloes", "seasons", "remote_error", "connected" }`: the local records merged with `liveBroadcasts.list broadcastStatus=completed broadcastType=all` (up to 100, read again after 10 minutes, `refresh=1` at most once a minute); a broadcast not in the record comes with `external: true` and escalão "Fora do Hallstream". YouTube's privacy wins for known ones. Newest first. `season` is "2026/27" (August to July, Lisbon). The lists of escalões and seasons cover every item, whatever the filters.
- A refused refresh (`invalid_grant`, or a 401) sets `expired`; the panel then says to connect again, in Definições, in the stream bar and as the YouTube chip.
- Quota (10 000 units a day): a game costs at most about 115: insert 1, bind 1, the reuse look 1, `thumbnails.set` 50, up to 10 looks after the stop, one transition 1, `videos.list` 1, `videos.update` 50. Transmissões costs 1 or 2 every 10 minutes at most.
- Panel: Definições > YouTube (fields, "Guardar", "Ligar ao YouTube", "Ligado como" with the channel picture, "Desligar"); the stream bar shows "No YouTube youtu.be/…" with "Copiar" while live; after Terminar a card under the bar: "A terminar no YouTube…", then "Vídeo não listado" with the link, "Copiar" and "Partilhar no WhatsApp" (`wa.me/?text=` with the result, the escalão and the link), or the error with "Tentar outra vez". Tab 6 Transmissões. Mock states: `?mock=1&yt=off|on|expired|ended|endfail`, `&thumb=fail`.

### Game logs (added by Go)
- `dados/timeline.jsonl`: one JSON line per change the video-stats side can't get from `raw.log`, each with `ts` (RFC 3339, milliseconds, local offset) and `event`: `stream_start` and `stream_stop` (`broadcast_id`, `""` without YouTube; `test`), `screen` (`name`; `auto` true when the program switched it: the automatic rules, or a promo clip that ended by itself), `lower_third` (`shown`, `type`, `number`; never names), `box` (`connected`), `game` (`key` as in "YouTube", `""` with no game picked; `home`, `away`; written when one of them changes, and at start), `period` (`period`, `home`, `away`, when a period is recorded; periods restored at start are not written again), `set` (`set`, `home`, `away`, when a set of a sets sport is recorded; sets restored at start are not written again). `suspension` (`team`, `number`, when a new suspension starts; never one restored at start), `card` (`team`, `number`, `kind`, `minute`) and `sub` (`team`, `out`, `in`, `minute`), when the scorer enters a card or a substitution (never one restored at start). Right after `stream_start` come `game`, `screen`, `lower_third` and `box` as they are then, each with `initial: true`. `stream_stop` carries the time the batch's cut ends at. Nothing is written while the demo runs (the initial `game` line excepted). Score and clock stay in `raw.log`.
- After each stream stops (Terminar, or OBS stopping by itself, test streams included) the program writes a batch to `dados/envios/<batch>/` and sends it to `settings.fpb_base_url` + `/api/marcador/logs` (`POST`, `Authorization: Bearer <token>`, the FPB client's `User-Agent`, multipart). The token only goes over https to `calendariofpb.pt` or a subdomain, redirects included; with `fpb_base_url` pointing elsewhere (`PUT /api/settings` takes it from a phone with the PIN too) nothing is sent, the batch stays pending and `marcador.log` says why once. `batch` is `<broadcast id>-<YYYYMMDD-HHMMSS>` (the stream's start, so two streams on one reused broadcast stay apart) when the id starts with a letter or digit and has only letters, digits, `.`, `_` and `-`, or `local-<YYYYMMDD-HHMMSS>` otherwise; `meta` is `meta.json`; each file is a `files[]` part named `raw.log.gz`, `timeline.jsonl.gz`, `marcador.log.gz`, `marcador.log.1.gz` (when there is one) and `bluetooth.log.gz`, all gzipped.
  - Every file holds only the lines from 30 minutes before the stream started to its end. The start is when OBS says the stream began, or the broadcast's `started_at` when that is earlier and at most 6 hours before it (a broadcast still on air across a restart of the program); it is never more than 6 hours before the end. `started_at` starts again when an ended broadcast is reused, and is cleared when OBS refuses to start. In `raw.log`, `timeline.jsonl` and `bluetooth.log` a line without a readable time is left out; in `marcador.log` (and `.1`) it goes with the line before it.
  - `marcador.log` with the Windows user's folder (any case, `\` or `/`) written as `~`, the bare user name as `(utilizador)`, any other `X:\Users\<name>` as `~`, and every player's name (`display_name`, `fpb_name`) as `(jogador)`: whole words, in any case, with or without accents. `bluetooth.log` only with the lines of likely boxes (`likely=true`): the rest are the phones and earphones of people in the hall.
  - Limits (the server's): at most 10 MB a gzipped file, 10 files and 25 MB a request (413 over that). A batch that would pass them keeps only the newest lines of `raw.log` that fit.
  - `meta`: `{ "version", "broadcast_id", "video_id", "title", "test", "escalao", "opponent", "stream_start", "stream_end" (RFC 3339 with offset), "score": { "home", "away" }, "box_address", "box_name" }`, plus `"truncated": true` when `raw.log` was cut to fit. Without a broadcast, `title` is the one the broadcast would have had and `escalao`/`opponent` come from the live game. Never the PIN, the OBS password, the YouTube client secret or any token.
  - A 200 deletes the batch. 401, 404, 429 and 5xx leave it for the next round. Any other 4xx (400, 413) is not retried: the batch moves to `dados/envios/falhados/` and the reason goes in `marcador.log`. Either way the round goes on to the newer batches; no network ends it. Errors are logged once until the next 200. Pending batches are tried oldest first at start and every 10 minutes. A batch with the name of one still waiting replaces it. `falhados` keeps the newest 20 batches; a batch pending for more than 60 days moves there, with a line in `marcador.log`.
  - The token comes from the build (`-X main.uploadToken=$HALLSTREAM_UPLOAD_TOKEN` in `build.sh`). Without it the program writes no batch, sends nothing and says so once in `marcador.log`.
  - `GET /api/status` → `uploads`: `pending` (batches waiting), `last_ok` (RFC 3339 of the last 200 since start, `""` before), `last_error` (`""` after a 200). The panel shows nothing new.

## Console capture

The panel's Marcação tab has a "Gravar a consola" switch (a card under the box's state, with the file's name, size and frame count while it runs, "Abrir a pasta das gravações", and "Como enviar o ficheiro", which opens Ajuda at "Um problema ou uma ideia"). Its help text says the file holds scoreboard frames only, that the team names in them are the ones typed into the console (often the club's name) so the file should be checked before it is sent in public, and to attach it to a report through Ajuda. It is off at every start and stays off in demo mode and while the box is not linked.

While it is on, the Bluetooth reader hands every raw notification to the recorder before decoding. The hand-over is a send on a buffered channel (4096 frames) that never blocks: when the writer falls behind, the frame is dropped and `dropped` counts it, and the reader carries on. One goroutine, started through `Server.once`, writes `dados/captura/captura-<YYYY-MM-DD_HH-MM-SS>.txt` (local time; `-2`, `-3` on a clash) and flushes whenever the channel empties. A recording stops when the switch goes off, when the box disconnects, when the next line would take the file past 50 MB (the log says so, and `stopped` is `cap`), or when the disk fails.

The file is text, one line per frame:

```
# hallstream capture 1 app="0.1.1" box="Livestream Stramatel" sport="futsal" start="2026-11-25T20:31:05Z"
0 7400000000000000000000000000000000000000
1042 33303734350000...
```

- The first line is the header: format version, the program's version, the box's Bluetooth name, the club's sport and the start time in UTC. Values are Go-quoted. The frames carry the team names typed into the console, often the club's name; nothing else about the club is written.
- Every other line is the offset in ms since the start, a space, and the frame in lowercase hex (20 bytes in practice). Offsets are taken when the frame arrives, not when it is written.
- Lines starting with `#` after the header are comments. `ble.ReadCapture` rejects a file without the header, any other line that is not `<ms> <hex>`, an offset over 7 days, more than 2,000,000 frames, and a file bigger than a recording plus its header.
- `internal/ble/testdata/basketball-synthetic.capture` is a hand-built basketball example (not a real game). Its decoded sequence is the golden `basketball-synthetic.golden`; `go test ./internal/ble -update` rewrites it.

`hallstream -replay <file>` reads a capture, uses the console as the score input whatever `settings.input` says, starts no Bluetooth reader, and plays the frames through the console at their recorded offsets, so the overlay moves as it did at the game. The console reads as connected from the start and stays so after the last frame; the program keeps running. An unreadable file stops the program with a message.

## Data folder (`dados/`, next to the .exe)
- `settings.json`, `groups.json` (groups with players and sponsor metadata), `game.json` (current game), `media/` (uploaded and downloaded images), `cache/fpb/*.json`, `jogos/<YYYY-MM-DD>-<group>.json` (history: game info, periods, final score), `raw.log` (every box frame, as now), `captura/` (console recordings, "Console capture"), `bluetooth.log` (devices heard while scanning), `marcador.log` (+ `marcador.log.1`, the program's messages), `score/*.txt` (the old text files, kept for existing OBS setups), `promo.json` and `promo/` (club videos, see "Promo videos"), `youtube.json` (the YouTube login, served only inside the backup below) and `transmissoes.json` (the streams), see "YouTube". `timeline.jsonl` and `envios/` (the game logs waiting to be sent, and `envios/falhados/`), see "Game logs".
- Writes are atomic (write temp, rename).
- Backup ("Guardar cópia", Definições > Cópia de segurança, shown only on the PC): `GET /api/system/backup` streams a zip named `Hallstream-copia-<YYYY-MM-DD>.zip` holding the whole folder under `dados/`, minus `raw.log*` (it grows all season) and `.tmp-*` files. Videos and pictures are stored, the rest deflated. A file deleted during the walk is skipped; any other error is logged and cuts the connection, so the browser shows a failed download. Only from the PC itself (403, also for a request another site sends, by `Sec-Fetch-Site`), since it holds the OBS password and the YouTube login. Restoring is by hand: with the program closed, unzip it into the program's folder. Ajuda > "Passar para outro computador" and the LEIA-ME give the steps.

## FPB Calendar endpoints (separate repo)
- `GET /api/teams?name=` (already there) → `[ { "id", "name", "age": "Sub 14", "gender": "Feminino", "slug", "squad_label": "Sub 14 F", "url", "has_fixtures" } ]`, current season only. Every request sends `User-Agent: hallstream/<version>` (Cloudflare blocks Go's default).
- `GET /api/teams/:id/next-games?days=14` → `{ "team": { "id", "name", "short_name", "logo_url" }, "games": [ { "id", "date": "2026-11-15", "time": "18H00", "location", "competition_name", "competition_slug", "game_week", "phase_name", "home": { "id", "name", "short_name", "logo_url" }, "away": { … } } ] }`, today and the next `days` days (max 60), sorted by date and time. `logo_url` falls back to `club_logo_url`.
- `GET /api/teams/:id/roster` → `{ "team": { "id", "name" }, "season", "players": [ { "player_id", "fpb_athlete_id", "name", "slug", "jersey_number", "photo_url", "games" } ] }`. `photo_url` is the FPB photo (`https://sav2.fpb.pt/uploads/…`) or `null`; older deploys without `fpb_athlete_id`/`photo_url` still decode (zero values): players with a `game_player_stats` row for this team in the team's season; `jersey_number` from their most recent game; sorted by jersey number.
- Both: 404 JSON for an unknown team, `Cache-Control: public, max-age=300`, inside the existing `api/ip` throttle.
